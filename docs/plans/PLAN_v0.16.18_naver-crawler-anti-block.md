# 네이버 크롤러 차단 회피 — 검증 계획 (v0.16.18)

> 상태: **추후 검증 예정** — 실측 전. (2026-08-14 작성)
> PLATFORM: server (로컬 워커)

## 배경 (운영 실측 2026-08-14)

로컬 워커의 네이버 브랜드스토어 크롤링에서 차단/슬로우가 관찰됨.

| 시나리오 | 결과 |
|---|---|
| 순차 (수정 전, 8.4s/건) | 정상 수집 |
| 병렬 3 (Chrome 동시 접속) | TimeoutError(45s 초과) + 가격 미발견 body 100자 다발 |
| 병렬 후 순차 복귀 | 50s/건 + 실패 지속 → **IP가 플래그된 상태** |

- 네이버는 단일 IP 기준 rate limit + 봇 탐지(헤더·핑거프린트·요청 규칙성)를 병행한다고 판단.
- 로컬은 **고정 IP**라 블랙리스트 시 회피 수단이 없어 보호가 중요.

## 관점 검토 — "1분에 1개씩, 매번 다른 상품"이면 안 막히나?

결론: **부분적으로만 맞다. 틀린 전제 3가지.**

1. **"사용자 = 배치"는 성립 안 함** — 사람은 하루에 상품 페이지 수십 개를 보다 멈추지만, 배치는 같은 IP로 24시간 쉬지 않고 요청. 1분 1개 = 하루 1,440건 → 봇으로 판정될 볼륨.
2. **규칙성 탐지** — 정확한 간격(60s) + 무휴식은 자동화 신호. 사람은 불규칙.
3. **상품 반복 여부는 판정의 핵심 신호 아님** — 네이버는 IP당 빈도·볼륨·패턴·헤더를 봄. 상품이 달라도 IP는 하나.

동의하는 부분: **템포 분산(몰아치기보다 간격)은 병렬보다 훨씬 안전** — 올바른 방향.

## 검증 계획

### 1. 분산 템포 실측 (1차 게이트)
- 방법: 네이버 브랜드스토어 상품 10건을 **30~90초 랜덤 간격**으로 순차 fetch.
- 판정: Timeout/가격 미발견 없이 수집 성공 + 상품당 ~8s 유지면 통과.
- 실패 시: 임계값이 더 낮은 것 → 간격 확대(120s+) 또는 볼륨 추가 축소.

### 2. 배치 변경 (실측 통과 시)
- 상품 사이 **랜덤 지연(30~90s)** 추가 (고정 간격 금지 — 규칙성 회피).
- 배치 크기 축소: 30건 → **10건 이하** (30건이면 15~45분 소요, 1시간 배치 간격 초과).
- 네이버는 **병렬 금지 유지** (실측으로 확정). 올리브영 병렬 3은 유지.

### 3. 볼륨 하한 (고정 IP 보호)
- 하루 요청 수 제한: 예) **100~200건/일** 이하.
- 초과 시 해당일 배치 스킵 (crawler_config로 조절 가능 확인).

### 4. 브라우저 제거 실측 (보너스 — 근본 해결 가능성)
- 네이버 상품 페이지를 **HTTP 직접 요청** → `og:price:amount` / `application/ld+json`(Product 스키마) / body 가격 존재 여부 확인.
- 성공 시: 브라우저(Playwright) 제거 → 상품당 1초대, 볼륨·차단 문제 자체가 사라짐.
- 실패 시: 모바일 페이지(`m.brand.naver.com`) / 브랜드스토어 내부 JSON API 실측.

## 결정 사항 (이미 확정)

- 네이버 `_parallel_workers()`: 기본 **순차(1)** — 병렬 시 차단 실측. (CRAWLER_PARALLEL 명시 시에만 병렬)
- 올리브영 `_parallel_workers()`: 로컬 기본 **병렬 3** — 배치 46% 단축 실측(388s→210s).
- 네이버 `wait_until="networkidle"` 유지 — domcontentloaded는 SPA 미로드로 가격 미발견 회귀 실측.

## 롤백 계획

- 실측 중 이상 시: 즉시 워커 중단(`pkill -f crawlers.worker`), IP 회복(10~30분) 후 재개.
- 배치 변경 후 실패율 급증 시: `CRAWLER_PARALLEL=1` + 랜덤 지연 제거로 복귀.
- 고정 IP 블랙리스트 시: 24h 이상 휴식 + 볼륨 하한 강화, 필요 시 프록시/유동 IP 도입 검토.
